Check for new images or apply updates on demand, read what the last run did, and feed Outpost into Prometheus, all over plain HTTP with an <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access token</Terminology>.

## Why Use This Feature?

1. Lets a CI pipeline check for a pushed image and apply it without waiting for the schedule.
2. Returns the overview, containers, and history as JSON so scripts can read them without parsing logs.
3. Streams live events so a script knows the moment a check finishes.
4. Exposes Prometheus counters so you can alert on failed or rolled-back updates.
5. Keeps Watchtower's `/v1/update`, `/v1/status`, and `/metrics` paths so existing clients keep working.

## Before You Start

- **A published port** — The API listens on port `22601`, next to the dashboard. The [Quick Start](/docs/getting-started/quick-start/) publishes it as `22601:22601`, which makes it reachable on every IPv4 and IPv6 address of the Docker host.
- **An <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access token</Terminology>** — Create one on the dashboard's **Access tokens** page with the <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scopes</Terminology> the client needs, as shown in [Access Tokens](/docs/features/access-tokens/).
- **The base URL** — The address the dashboard is open at, such as `http://192.168.1.50:22601`. Every path starts at the root, so a sub-path isn't supported.

## Authentication

Send the token in the `Authorization` header of every request:

```bash
# Read the token without showing it or saving it to the shell history.
read -r -s OUTPOST_TOKEN

curl --header "Authorization: Bearer $OUTPOST_TOKEN" http://127.0.0.1:22601/api/v1/overview
```

- The word `Bearer` is matched without regard to letter case. A token is `outpost_` followed by 43 URL-safe base64 characters.
- A missing, mistyped, expired, or revoked token gets `401` with the code `authentication_required`.
- A valid token without the route's <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scope</Terminology> gets `403` with the code `scope_required`.
- `GET /api/v1/auth/me` works with any valid token and returns its name and <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scopes</Terminology>, which makes it a handy first test.

The `/api/v1` data routes also accept a browser that is signed in to the dashboard, and a token in the header wins over the browser's cookie. The Watchtower-style paths take tokens only.

|----------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `status:read`  | See the overview, containers, history, and settings.                                                                                                                                                                | `GET /api/v1/overview`, `GET /api/v1/containers`, `GET /api/v1/history`, `GET /api/v1/settings`, `GET /api/v1/status`, `GET /api/v1/events`, `GET /v1/status` |

## Start a Check

`POST /api/v1/checks` is check-only. It compares each selected running image with its registry digest, records `available` for newer images, and never pulls an image or recreates a container. The response body stays `{"started":true}` for compatibility with existing clients.

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  http://127.0.0.1:22601/api/v1/checks
```

To check one container, send its 12-character ID from `GET /api/v1/containers`:

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"containerId":"3f2a9c1b7d4e"}' \
  http://127.0.0.1:22601/api/v1/checks
```

| Status | Meaning                                                                                                                                                                                                        |
|--------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `202`  | A <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> started, and the body is `{"started":true}`.                          |
| `409`  | A <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> is already running, so none was started. The code is `check_running`. |
| `422`  | The `containerId` isn't 12 to 64 hexadecimal characters, or the body has another field. The code is `invalid_request`.                                                                                         |

- The request returns right away. Watch `GET /api/v1/events`, or poll `GET /api/v1/status` until `running` is `false`, to read the results.
- Without `Content-Type: application/json`, the body isn't read, so Outpost checks every container.
- An ID of a container that Outpost doesn't manage starts a check that changes nothing.
- Outpost's own ID, from the row where `self` is `true`, checks Outpost itself without restarting it.
- The dashboard's **History** page shows **API** as what started the check.

## Apply Updates

Apply updates to every managed container:

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  http://127.0.0.1:22601/api/v1/updates
```

Or update one container by sending the same `containerId` shape as the check endpoint:

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"containerId":"3f2a9c1b7d4e"}' \
  http://127.0.0.1:22601/api/v1/updates
```

`rollback` is a boolean and defaults to `true`. To keep one failed replacement for inspection instead of restoring its previous container, send `rollback: false` with its `containerId`:

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"containerId":"3f2a9c1b7d4e","rollback":false}' \
  http://127.0.0.1:22601/api/v1/updates
```

The override is deliberately narrow. `rollback: false` without `containerId`, or with the ID whose container row has `self: true`, returns `422 invalid_request`. It never applies to `POST /v1/update`, **Update all**, scheduled updates, startup updates, or Outpost itself. A wrong type for `rollback` also returns `422`.

When rollback is disabled, a failed replacement has status `kept-unhealthy` and counts as a failure. Outpost leaves it as Docker left it, keeps the previous image even when cleanup is on, and renames the stopped previous container to a unique name such as `web-outpost-kept-20261024T040112Z`. The result detail records that exact name, its container ID, its image ID, and a non-secret configuration summary. The saved report and notifications say rollback was disabled. This explicit request also retries an image that an earlier run rolled back; ordinary updates keep waiting for a newer image.

The endpoint otherwise returns the same `202`, `409`, and `422` shapes as `POST /api/v1/checks`. It runs the full update cycle, including pull, recreation, health checks, rollback, and cleanup. Outpost updates itself last. Global or per-container <Terminology title="Tells you about updates but never applies them" to="/docs/reference/terminology#container-selection">monitor-only</Terminology> settings still report an available image without applying it.

## Read the Status

```json title="GET /api/v1/status"
{
  "running": false,
  "nextRun": "2026-10-25T04:00:00.000Z",
  "lastReport": {
    "action": "update",
    "startedAt": "2026-10-24T04:00:00.012Z",
    "finishedAt": "2026-10-24T04:01:12.480Z",
    "results": [
      {
        "container": "web",
        "image": "ghcr.io/example/web:latest",
        "status": "updated",
        "detail": "Recreated with ghcr.io/example/web:latest"
      }
    ],
    "trigger": "schedule"
  },
  "totals": {
    "cycles": 3,
    "updated": 1,
    "failed": 0
  }
}
```

- **`running`** — `true` while a <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> runs. While it is `true`, `action` is `check` or `update`, and `startedAt` shows when it began. Scheduled and startup runs use `update`, or `check` while **Monitor only** is on in **Settings**.
- **`nextRun`** — When the schedule starts the next <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology>.
- **`lastReport`** — The newest entry in the saved history, so it survives a restart when `/data` is on a volume. Its `action` is `check` or `update`, and its `trigger` names what started it: `schedule`, `startup`, `api`, or `dashboard`. A run that disabled rollback has `"rollback": false`; ordinary and older reports omit it. Reports saved before `action` existed were update cycles and omit that field too.
- **`lastError`** — Present only when the last <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> failed as a whole, for example because the Docker socket was unreachable.
- **`totals`** — Counted since Outpost started, and reset when it restarts.

`GET /api/v1/overview` returns the same fields, plus `schedule`, `timeZone`, `labelMode`, and `monitorOnly`. `timeZone` is the time zone the schedule runs in, which `TZ` sets.

## Live Events

`GET /api/v1/events` keeps the connection open and sends server-sent events:

```bash
curl --no-buffer \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  http://127.0.0.1:22601/api/v1/events
```

```text title="Event stream"
retry: 3000

event: state
data: {"running":false,"nextRun":"2026-10-25T04:00:00.000Z","totals":{"cycles":0,"updated":0,"failed":0},"schedule":"0 0 4 * * *","timeZone":"UTC","labelMode":"opt-out","monitorOnly":false}

: keep-alive
```

- **`state`** — The overview object, sent when you connect and whenever a check or update starts or finishes. While `running` is `true`, its `action` distinguishes `check` from `update`.
- **`check`** — The <Terminology title="What happened to each container in one check" to="/docs/reference/terminology#update-cycles">report</Terminology> of a check or update that just finished. The event name remains `check` for compatibility; read the report's `action` to distinguish them.
- **Keep-alive** — A comment line every 15 seconds keeps proxies from closing the stream. A revoked token or a signed-out browser stops getting events at the next one.

## Errors

Failed requests return the same JSON shape, with a stable `code` for scripts and a `message` for people. The one exception is `POST /v1/update`, which answers a running check with `{"started":false}`.

```json title="A failed request"
{
  "error": {
    "code": "scope_required",
    "message": "This token doesn't have the updates:run scope."
  }
}
```

A body that fails validation also lists each problem in `issues`, with the `field`, a `message`, and the `path`:

```json title="A body that failed validation"
{
  "error": {
    "code": "invalid_request",
    "message": "Use a container ID of 12 to 64 hexadecimal characters.",
    "issues": [
      {
        "field": "containerId",
        "message": "Use a container ID of 12 to 64 hexadecimal characters.",
        "path": ["containerId"]
      }
    ]
  }
}
```

| Status | Code                      | When                                                                                                                                                                             |
|--------|---------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `400`  | `invalid_json`            | The body isn't valid JSON.                                                                                                                                                       |
| `401`  | `authentication_required` | The token is missing, mistyped, expired, or revoked, or no browser is signed in.                                                                                                 |
| `403`  | `scope_required`          | The token doesn't have the route's <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scope</Terminology>. |
| `403`  | `session_required`        | A token was sent to a route that only the dashboard can use.                                                                                                                     |
| `403`  | `csrf_invalid`            | A signed-in browser sent a change without its CSRF token.                                                                                                                        |
| `404`  | `not_found`               | No route matches the method and path, such as `GET /v1/update`.                                                                                                                  |
| `409`  | `check_running`           | A check or update is already running.                                                                                                                                            |
| `413`  | `payload_too_large`       | The body is larger than 64 KB, or 10 MB for `/api/v1/backup` routes.                                                                                                             |
| `415`  | `unsupported_encoding`    | The body isn't UTF-8, or it uses a compression Outpost can't read.                                                                                                               |
| `422`  | `invalid_request`         | A field is missing or breaks a rule, and `issues` names it.                                                                                                                      |
| `429`  | `rate_limited`            | The client sent too many requests.                                                                                                                                               |
| `500`  | `internal_error`          | Something unexpected went wrong, and the container log has the cause.                                                                                                            |
| `502`  | `docker_unreachable`      | Outpost can't reach Docker.                                                                                                                                                      |

Outpost checks a request in this order, so the first problem it finds decides the answer:

1. The JSON body, for `400`, `413`, or `415`.
2. The rate limit, for `429`.
3. The token or the browser sign-in, for `401` or `403`.
4. The fields in the body, for `422`.

## Rate Limits

- Every request to a path under `/api/v1`, `/v1`, or `/metrics` counts toward 120 requests per minute for each client address, or each `/56` network for IPv6. The dashboard's own requests count too.
- Responses carry the `RateLimit-Policy`, `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` headers. A `429` also carries `Retry-After` in seconds.
- Sign-in has its own limit on failed attempts, described in [Web Dashboard](/docs/features/dashboard/#failed-sign-ins).
- Behind a reverse proxy, the client address comes from `X-Forwarded-For`, as described in [Web Dashboard](/docs/features/dashboard/#behind-a-reverse-proxy).

## Watchtower-Style Endpoints

`POST /v1/update`, `GET /v1/status`, and `GET /metrics` keep the bodies that Watchtower-style clients expect. They take an <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access token</Terminology> only, never a browser sign-in.

### Trigger an Update

```bash
curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  http://127.0.0.1:22601/v1/update
```

| Status | Body                | Meaning                                                                                                                                                                           |
|--------|---------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `202`  | `{"started":true}`  | A new <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> started.                             |
| `409`  | `{"started":false}` | A <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> is already running, so none was started. |

- `POST /v1/update` always runs a full <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> and ignores query parameters. To update one container, use `POST /api/v1/updates` instead; to check without applying anything, use `POST /api/v1/checks`.
- Other failures, such as a missing token, use the error shape described in [Errors](#errors).

### Status and Metrics

`GET /v1/status` returns the same body as `GET /api/v1/status`, described in [Read the Status](#read-the-status). `GET /metrics` returns the Prometheus text described in [Metrics](#metrics).

## Metrics

Point Prometheus at `/metrics` with a token that has the `metrics:read` <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scope</Terminology>:

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: outpost
    authorization:
      # A token with the metrics:read scope.
      credentials: outpost_...
    static_configs:
      - targets:
          - outpost:22601
```

| Metric                                 | Type    | Description                                                                                                                                                                                |
|----------------------------------------|---------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `outpost_cycles_total`                 | counter | Update cycles finished since start, including single-container checks and cycles that failed as a whole.                                                                                   |
| `outpost_containers_updated_total`     | counter | Containers updated since start.                                                                                                                                                            |
| `outpost_containers_failed_total`      | counter | Container updates that failed, rolled back, or were kept after failure since start.                                                                                                        |
| `outpost_cycle_running`                | gauge   | `1` while a <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> is running, otherwise `0`.              |
| `outpost_last_cycle_timestamp_seconds` | gauge   | Unix time the last <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> finished. Missing until one has. |

A useful alert is `increase(outpost_containers_failed_total[1d]) > 0`, which fires when any update failed, rolled back, or kept a failed replacement in the last day.

- Routes for a browser need one that is signed in to the dashboard. A token gets `403` with the code `session_required`, so a token can't change sign-in settings, make more tokens, or read or change notification <Terminology title="Where your alerts land, like ntfy, Telegram, or email" to="/docs/reference/terminology#notifications">destinations</Terminology>.
- Every change from a browser also needs the sign-in's CSRF token in the `X-CSRF-Token` header, or it gets `403` with the code `csrf_invalid`.
- For a browser, `GET /api/v1/auth/me` also returns `removedSecrets`, an empty list normally. After a lost <Terminology title="The file that unlocks your saved secrets" to="/docs/reference/terminology#backup-and-encryption">encryption key</Terminology>, it holds `{"kind":"authenticator","removedAt":"2026-10-25T08:30:00.000Z"}` for the authenticator app, and `{"kind":"notification","name":"Homelab chat","notificationId":"ntf-6a8c0e2b4d6f8a13","removedAt":"2026-10-25T08:30:00.000Z"}` for each <Terminology title="Where your alerts land, like ntfy, Telegram, or email" to="/docs/reference/terminology#notifications">destination</Terminology> that lost secrets.
- An entry leaves the list when its secret is entered again, and `DELETE /api/v1/auth/removed-secrets`, which answers `204`, empties it.
