Start Outpost next to your other containers and let it check them for new images every night.

## Prerequisites

- **Docker Engine** — On Linux, for `amd64` or `arm64`.
- **Docker socket** — Outpost talks to Docker through `/var/run/docker.sock`, which you mount into the container.
- **A user ID and group ID** — Outpost runs as `PUID` and `PGID` (both `1000` by default and each from `1` through `60000`) and joins the socket's group on its own. The container starts as root so s6 can prepare state and drop the server to those IDs.

## Pick an Image

Each release publishes the same multi-platform image to both registries:

- `cbnventures/outpost` on [Docker Hub](https://hub.docker.com/r/cbnventures/outpost)
- `ghcr.io/cbnventures/outpost` on the GitHub Container Registry

Use either registry for a released image. To try an unpublished working copy, build it from source with the repository's own `compose.yml`, as shown below.

### Build From Source

Clone the repository and let Docker Compose build and start Outpost from its `compose.yml`:

```bash
git clone https://github.com/cbnventures/outpost.git
cd outpost

# Build the image and start Outpost in the background.
docker compose up --build --detach
```

The image is built and tagged `cbnventures/outpost:latest` on your host, and Outpost starts with the settings in that `compose.yml`, which reads overrides such as `TZ` from a `.env` file next to it. Skip ahead to [Check That It Started](/docs/getting-started/quick-start/#check-that-it-started), and run `docker compose logs outpost` from the clone wherever this page uses `docker logs outpost`.

Outpost skips this image as locally built, so it doesn't update itself. On Docker 28 or older with the containerd image store, Docker doesn't record that the image was built here, so once a release is published Outpost could replace your build with it; label the container `io.cbnventures.outpost.enable=false` to keep it.

## Start Outpost

<Tabs groupId="deployment-method">
  <TabItem value="compose" label="Docker Compose" default>

    ```yaml title="compose.yml"
    services:
      outpost:
        image: cbnventures/outpost:latest
        container_name: outpost
        environment:
          PGID: "1000"
          PUID: "1000"
          TZ: "America/New_York"
        network_mode: host
        restart: always
        user: "0:0"
        volumes:
          - /var/run/docker.sock:/var/run/docker.sock

          # Keeps the dashboard account, access tokens, notification destinations,
          # registry sign-ins, and history across restarts, and lets Outpost
          # update itself.
          - outpost-data:/config

    volumes:
      outpost-data:
    ```

    ```bash
    docker compose up --detach
    ```

  </TabItem>
  <TabItem value="docker-run" label="docker run">

    ```bash
    docker run --detach \
      --name outpost \
      --restart always \
      --env PGID=1000 \
      --env PUID=1000 \
      --env TZ=America/New_York \
      --user 0:0 \
      --net=host \
      --volume /var/run/docker.sock:/var/run/docker.sock \
      --volume outpost-data:/config \
      cbnventures/outpost:latest
    ```

  </TabItem>
</Tabs>

Earlier Outpost versions mounted state at `/data`. Reuse the same host folder or named volume at `/config`; on first start, Outpost preserves the key and moves the flat SQLite files into `database/` without overwriting existing state.

An unchanged old run line that mounts only `/data` also starts safely. Outpost uses that mount, performs the same layout migration under `/data`, and logs a reminder to change the mount target to `/config`.

By default, Outpost checks every running container at 04:00 in your time zone. New images are pulled and the containers are recreated on them. The schedule and update behavior can be changed later from the dashboard's **Settings** page.

:::info
Outpost checks its own container last and hands it to a short-lived helper container, which swaps it onto the new image, as described in [Updates and Rollback](/docs/features/updates-and-rollback/#how-outpost-updates-itself). Outpost finds that container from Linux process metadata, with Docker's container-ID hostname only as a fallback, so host networking or a custom hostname doesn't hide it.

If Outpost can't find its own container, it leaves alone every container running an image named `outpost`, such as `cbnventures/outpost:latest`, so it never stops itself in the middle of a check.
:::

## Check That It Started

Read the container logs:

```bash
docker logs outpost
```

A healthy start prints the dashboard address, the schedule with its next run time in UTC, and the <Terminology title="Update everything by default, or only what you label" to="/docs/reference/terminology#container-selection">label mode</Terminology>. Until the dashboard account exists, it also prints a <Terminology title="One-time code from the log that creates your account" to="/docs/reference/terminology#dashboard-sign-in">setup code</Terminology>:

```text
2026-10-24T22:00:00Z INFO server: Dashboard: http://localhost:22601/admin/
2026-10-24T22:00:00Z INFO server: Schedule: 0 0 4 * * * (next run 2026-10-25T08:00:00.000Z)
2026-10-24T22:00:00Z INFO server: Mode: opt-out
2026-10-24T22:00:00Z INFO server: No account exists yet. Open the dashboard to create it with the setup code.
2026-10-24T22:00:00Z INFO server: Setup code: K7Q2M-XR9TD-P4W8N
2026-10-24T22:00:00Z INFO server: Setup code expires: 2026-10-24T22:30:00.000Z
```

Docker also checks that every supervised service is up and that `GET /health` answers `200` on port `22601`. Confirm its result with `docker inspect --format '{{.State.Health.Status}}' outpost`; a ready container reports `healthy`.

If Outpost can't reach the Docker socket, the server stops before printing this and the error repeats in the logs. See [Troubleshooting](/docs/reference/troubleshooting/#permission-denied-on-the-docker-socket) for the fix.

## Open the Dashboard

Open [http://localhost:22601/admin/](http://localhost:22601/admin/) on the Docker host, or `http://<server-ip>:22601/admin/` from another computer on its network. The first time, it asks you to set up your account:

1. Enter the <Terminology title="One-time code from the log that creates your account" to="/docs/reference/terminology#dashboard-sign-in">setup code</Terminology> from the log under **One-time code**. A code works for 30 minutes, and restarting the container prints a new one.
2. Choose a username and a password of 12 to 1,024 characters, and repeat the password under **Confirm password**.
3. Select **Create account**.

The dashboard then opens signed in. It shows every running container, the next scheduled check, and the results of past checks.

## Run a First Check Now

You don't have to wait for the schedule. Pick one of these check-only actions:

- **Use the dashboard** — Select **Check now** on the overview.
- **Trigger it over HTTP** — Create an <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access token</Terminology> with the `updates:run` <Terminology title="What a token may do, such as read status or run updates" to="/docs/reference/terminology#api-access">scope</Terminology> on the dashboard's **Access tokens** page, then call the checks endpoint as shown in [HTTP API and Metrics](/docs/features/http-api-and-metrics/#start-a-check).

```bash
# Paste the token and press Enter. It isn't shown or saved to the shell history.
read -r -s OUTPOST_TOKEN

curl --request POST \
  --header "Authorization: Bearer $OUTPOST_TOKEN" \
  http://127.0.0.1:22601/api/v1/checks
```

The check resolves registry digests and records available updates without pulling or recreating anything. Each container gets one line in the logs when the <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> finishes:

```text
2026-10-24T22:05:00Z INFO scheduler: postgres (postgres:17): up-to-date - sha256:9c1d...
2026-10-24T22:05:00Z INFO scheduler: web (ghcr.io/example/web:latest): available - New digest sha256:7a3e...
2026-10-24T22:05:00Z INFO scheduler: outpost (cbnventures/outpost:latest): up-to-date - sha256:4e7b...
```

:::tip
Select **Update all** after the check to apply every available managed update, or use the **Update** action on one container. Scheduled runs and **Check when Outpost starts** still apply updates automatically; turn on **Monitor only** if those automatic runs should only report them.
:::
