Set update behavior from the **Settings** page. Outpost saves those choices in SQLite and applies them immediately, while Compose remains responsible for the paths and identity needed before that database can open.

## Two Kinds of Configuration

1. **Runtime behavior** — The schedule, label mode, monitor-only mode, cleanup, replacement timing, and private registry sign-ins live in the database. Change them on the **Settings** page without restarting Outpost.
2. **Container bootstrap** — The Docker connection, data directory, process identity, time zone, and port remain in Compose because Outpost needs them before it can read the database.

Back up the `outpost-data` volume to preserve the runtime settings with the account, access tokens, notification destinations, registry sign-ins, and history.

## Example

```yaml title="compose.yml"
services:
  outpost:
    image: cbnventures/outpost:latest
    container_name: outpost
    environment:
      PGID: "1000"
      PUID: "1000"
      TZ: "Europe/London"
    network_mode: host
    restart: always
    user: "0:0"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - outpost-data:/config

volumes:
  outpost-data:
```

After Outpost starts, open **Settings** to choose the schedule and update behavior, and to add sign-ins for [private registries](/docs/getting-started/private-registries/#add-a-sign-in).

## Schedule Settings

| Setting                       | Description                                                                                                                                                                                                                                                                        |
|-------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Schedule**                  | **Every hour**, **Every few hours** (2, 3, 4, 6, 8, or 12), **Every day** or **Every week** on the days you pick at a set time, or **Custom (cron)** for a cron expression. Default every day at 04:00. The line under it shows the next check.                                    |
| **Check when Outpost starts** | Starts an automatic update <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> as soon as Outpost starts, or a check while **Monitor only** is on, in addition to the schedule. Off by default. |

The schedule runs in the time zone set by `TZ`, which the next-check line names. **Custom (cron)** takes six fields, second, minute, hour, day of month, month, and day of week, for example:

- `0 0 4 * * *` — Every day at 04:00.
- `0 0 */6 * * *` — Every six hours.
- `0 30 2 * * 0` — Sundays at 02:30.

Five-field patterns without the seconds field, such as `0 4 * * *`, also work, as do the nicknames `@yearly`, `@monthly`, `@weekly`, `@daily`, and `@hourly`.

If a <Terminology title="One check-and-update pass over your containers" to="/docs/reference/terminology#update-cycles">cycle</Terminology> is still running when the schedule comes due, that scheduled run is dropped, not queued. The next one starts at its usual time.

## Update Behavior Settings

| Setting                 | Description                                                                                                                                    |
|-------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| **Container selection** | **Opt-out** updates every container unless labeled off; **Opt-in** updates only labeled containers. Default **Opt-out**.                       |
| **Monitor only**        | Reports newer images without recreating any container. Scheduled and startup runs become registry-only checks that never pull. Off by default. |
| **Clean up old images** | Removes the old image after a successful update when nothing else uses it. On by default.                                                      |
| **Stop timeout**        | Seconds Docker waits for the old container to stop before killing it. Default `30`.                                                            |
| **Health timeout**      | Seconds a new container with a healthcheck has to report healthy. Default `120`.                                                               |
| **Settle time**         | Seconds a new container without a healthcheck must keep running before the update counts. Default `10`.                                        |

See [Labels and Modes](/docs/features/labels-and-modes/) for the label rules and [Updates and Rollback](/docs/features/updates-and-rollback/) for how the timeouts are used.

## State Directory

App state lives at `/config`, with this layout:

| Path                                 | Purpose                                                                                                                                                                                                                                                                              |
|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `/config/keys/installation.key`      | The 32-byte <Terminology title="The file that unlocks your saved secrets" to="/docs/reference/terminology#backup-and-encryption">encryption key</Terminology>, stored as 64 lowercase hexadecimal characters plus a newline. The folder is mode `0700`, and the file is mode `0600`. |
| `/config/database/outpost.sqlite3`   | The dashboard account, runtime settings, <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access tokens</Terminology>, notification destinations, and private registry sign-ins.                                             |
| `/config/database/outpost.sqlite3-*` | SQLite's write-ahead log and shared-memory companions when they exist.                                                                                                                                                                                                               |
| `/config/history.json`               | The last 50 checks and updates.                                                                                                                                                                                                                                                      |
| `/config/image-config-cache.json`    | Image defaults needed to recreate containers accurately.                                                                                                                                                                                                                             |
| `/config/self-update.json`           | A self-update that is in progress or a new Outpost image that failed.                                                                                                                                                                                                                |

Nova's initializer resolves the active state folder and exports `NOVA_STATE_DIRECTORY`, `NOVA_KEYS_DIRECTORY`, `NOVA_INSTALLATION_KEY_FILE`, `NOVA_DATABASE_DIRECTORY`, and `OUTPOST_DATA_DIRECTORY` to the server. It recursively changes the complete state directory to `PUID:PGID` on every start, then restores the key permissions.

`/data` is not used for new Outpost state. Existing installations may keep an old `/data`-only mount for this release; the initializer detects it and uses it without data loss, while a host folder remounted at `/config` is migrated there automatically.

The dashboard account, runtime settings, <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access tokens</Terminology>, notification <Terminology title="Where your alerts land, like ntfy, Telegram, or email" to="/docs/reference/terminology#notifications">destinations</Terminology>, and private registry sign-ins are kept in the database directory.

You create the account on the first visit, with a <Terminology title="One-time code from the log that creates your account" to="/docs/reference/terminology#dashboard-sign-in">setup code</Terminology> from the container log, as shown in [Web Dashboard](/docs/features/dashboard/#set-up-your-account). <Terminology title="Where your alerts land, like ntfy, Telegram, or email" to="/docs/reference/terminology#notifications">Destinations</Terminology> are added on the **Notifications** page, as shown in [Notifications](/docs/features/notifications/#add-a-destination).

:::info
Behavior settings, such as the schedule, label mode, monitor-only, cleanup, and timeouts, live on the **Settings** page, not in environment variables. Private registry sign-ins are added there too, as described in [Private Registries](/docs/getting-started/private-registries/#add-a-sign-in), and a reverse proxy needs no setting, as described in [Web Dashboard](/docs/features/dashboard/#behind-a-reverse-proxy).
:::

## Docker Connection

| Variable      | Description                                                                                                    |
|---------------|----------------------------------------------------------------------------------------------------------------|
| `DOCKER_HOST` | Docker Engine address: a `unix://` socket or a plain `tcp://host:port`. Default `unix:///var/run/docker.sock`. |

`DOCKER_HOST` doesn't support TLS, so a `tcp://` address is best kept to a socket proxy on a private network.

## Container Identity

| Variable | Description                                                                                    |
|----------|------------------------------------------------------------------------------------------------|
| `PUID`   | User ID the Outpost process runs as, from `1` through `60000`. Default `1000`.                 |
| `PGID`   | Group ID the Outpost process runs as, from `1` through `60000`. Default `1000`.                |
| `TZ`     | IANA time zone the schedule and container clock use, such as `America/Chicago`. Default `UTC`. |

The container starts as root so the initializer can change ownership and write `/etc/localtime` and `/etc/timezone`. The server then runs as `PUID:PGID` and also joins the group that owns the Docker socket, so `PGID` doesn't need to match the `docker` group.

## Port

Outpost is assigned fixed port `22601` in CBN Ventures' `22600`–`22699` Docker port block. The standard host-network setup needs no port mapping, so the dashboard and HTTP API use port `22601` on the Docker host.

## Health Check

Docker runs the generated health check every 30 seconds, with a 5-second timeout, 30-second start period, and three retries. It reports healthy only when every required s6 service is up and `GET /health` answers `200` on port `22601`.

The server is critical. If it exits, s6 stops the container, and the shutdown timing keeps the complete stop within Docker's default 10 seconds.

## Logs

Every initializer, supervisor, and application record is one plain-text line in this shape:

```text
2026-10-24T22:05:00Z INFO scheduler: web (ghcr.io/example/web:latest): updated - Recreated on the new image
```

The fields are an ISO UTC time, `DEBUG`, `INFO`, `WARN`, or `ERROR`, a component, and one fact. Outpost never emits JSON logs; turn on **Debug logging** under **Settings** only when the extra timing records are useful.

## Backup

Near the end of **Settings**, just above **Diagnostics**, is **Backup**, with **Export…** and **Import…** beside **Export and import**. It works independently of the settings save bar and makes a portable <Terminology title="A JSON backup you can carry to another Outpost" to="/docs/reference/terminology#backup-and-encryption">export file</Terminology> for selected settings, private registry sign-ins, notifications, and <Terminology title="A key your scripts send to call the API" to="/docs/reference/terminology#api-access">access-token</Terminology> hashes.

An import previews which values will be replaced, added, or skipped before it changes anything. See [Export and Import](/docs/reference/backup-and-recovery/#export-and-import) for the wizard steps and the difference between a portable file and a complete data-directory backup.

## Validation

The **Settings** page validates runtime behavior before saving it:

- **Timing values** — Must be positive whole numbers.
- **Container selection** — Must be `opt-in` or `opt-out`.
- **Schedule** — Must be a pattern the cron parser accepts. An invalid pattern remains unsaved and is highlighted on the page.

Outpost checks bootstrap values at startup and refuses to start when one is invalid:

- **`PUID` and `PGID`** — Must be whole numbers from `1` through `60000`, so `0` and larger IDs are refused. The image's init step logs `PUID must be an integer between 1 and 60000.` or the matching `PGID` message.
- **`TZ`** — Must name a time zone installed in the image, such as `America/Chicago`. Otherwise the init step logs `Unknown timezone:` followed by the value.
- **<Terminology title="The file that unlocks your saved secrets" to="/docs/reference/terminology#backup-and-encryption">Encryption key</Terminology>** — The key file in the data directory must belong to the database, or startup stops, as described in [Backup and Recovery](/docs/reference/backup-and-recovery/#encryption-key-doesnt-match). A missing key file doesn't stop startup, because Outpost makes a new key, turns off the authenticator app, and removes the <Terminology title="A saved token or password the API never hands back" to="/docs/reference/terminology#notifications">secret fields</Terminology> of notification <Terminology title="Where your alerts land, like ntfy, Telegram, or email" to="/docs/reference/terminology#notifications">destinations</Terminology> and the saved registry passwords.

`DOCKER_HOST` is not checked for format. A wrong address stops Outpost at startup when its Docker connection fails.
